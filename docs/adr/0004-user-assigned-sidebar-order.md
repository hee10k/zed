# User-assigned sidebar order as an explicit nullable column, falling back to recency

The sidebar thread list gets user-controllable ordering via drag-and-drop. Threads and terminals share a single explicit, persisted, integer `order` per project group; entries the user has never reordered carry no value and fall through to the existing recency sort (`thread_display_time`), grouped after explicitly-ordered entries. The `order` lives as a nullable column in both the thread and terminal metadata stores.

**Considered:** a pure manual-reorder model replacing recency entirely — rejected because newly-created threads and terminals would land in an arbitrary position and the default sidebar would need a migration for every user, breaking the "unchanged until touched" guarantee. A separate order list keyed by entry id was also considered and rejected in favour of a nullable column on the row itself, which avoids an extra index and keeps unsetness explicit. **Consequences:** sort logic must handle a partial order — ordered entries first (by order value), then unordered entries by recency; two stores need the same nullable `order` column, so the sidebar merge of threads and terminals must reconcile ordering across both sources in one pass.
